# Release recovery engine

Release-enabled startup queues read-only reconciliation of interrupted publication jobs under the existing per-repository owner gate. It does not restart queued writes. Planning can start while forge reads are pending or unavailable. The engine's `ReleaseReconciliation.reconcile(jobId)` repeats independent reads explicitly; HTTP and CLI exposure are separate work.

An exact tag and release become complete only after a new immutable reconciliation receipt is durably finalized. The publication points to that reconciliation job, while older receipts remain historical evidence. An artifact failure stays an internal error even if remote state is exact. Inspect the original plan and approval intent, restore private writable storage, and reconcile again; do not replay publication to repair a receipt.

Exact-tag/missing-release and absent/absent observations block ordinary publication. Preparation can create a new recovery plan that retains the original candidate, version, title, notes and frozen tag object. It verifies that the candidate remains reachable from the current default branch and binds the current branch head into the new digest. A new approval is required. An accepted recovery intent supersedes its predecessor for admission decisions without deleting that predecessor's evidence. A further interruption requires another reconciliation and newly reviewed recovery plan. Later execution must recheck the recovery plan's captured default-branch head along with its other approval-relevant evidence before any missing effect.

Conflict, unknown state, missing approval intent, changed identity or unreadable durable evidence never authorize recovery writes. The job detail and human-readable receipt name inspection, finalization or recovery steps. Receipts report point-in-time observations and actual observed authors, not permanent remote immutability. Late effects and external actors can still race with manual recovery.

## Approved publication execution

`ReleasePublication.execute(jobId)` is an engine-only interface, not an HTTP route or a startup queue runner. It consumes only a queued job with matching durable approval accepted before its stored deadline. An accepted job may finish after expiry. Preparation freezes a digest of the non-secret repository configuration, including the SSH push origin, key/trust paths, API credential selector, designated CI policy and tagger; a change requires a fresh plan. Credential bytes are excluded and authenticated numeric identity is independently renewed.

Execution restores the exact frozen annotated object, verifies repository/account/default-branch identity, original or recovery candidate, stable-tag baseline, and the exact selected CI run. It renews branch/identity evidence after CI reads and proves reviewed tag/release state before one explicit non-force object-to-tag push. The durable intent and `creating-tag` marker precede that effect. Generic pushes, force, ref deletion and automatic write retries have no interface. Shutdown interruption affects the bounded push, not the subsequent independent reconciliation reads. Post-attempt reads and receipt finalization remain inside the publication's already-admitted ownership operation, so graceful shutdown drains them before releasing the lock without reopening admission.

After a tag attempt, execution renews identity, configuration, candidate, baseline, exact CI and intent checks, then independently proves the exact tag and authoritative release absence before creating the approved release. A plan with an already-exact tag needs no push. The only HTTP mutation interface sends one origin-restricted, redirect-refusing POST with the frozen tag, title and notes and stable non-draft/non-prerelease flags. It sends no assets, target commitish or tag-creation message, and exposes no edit, delete or upload operation. Gitea can still manufacture a tag if an external actor removes it between proof and creation; the engine does not rely on this behavior and independently checks the final tag object.

After every attempted create request, including success, error status, timeout, interruption, silent response or lost response, the existing read-only reconciler independently inspects both objects and finalizes an immutable receipt. Only exact/exact with a durable receipt completes. An approved exact/exact plan is a verified no-op; the receipt retains the actual release author, not an attribution to this job. Missing effects require a newly approved original-version recovery; conflict/unknown needs inspection. No write is replayed automatically. Durable pre-launch effect markers survive a crash and are copied into the final receipt; a recorded attempt means the effect may have reached the remote. A crash before reconciliation leaves the original consumed job/intent for startup inspection. Graceful shutdown interrupts the request but drains independent reads and receipt finalization within the already-admitted owner operation. External and late effects remain point-in-time risks; there is no automatic rollback. HTTP publication remains unavailable until its dedicated route slice.

## State compatibility and rollback

Schema 1 remains readable without migration. New optional fields are `ReleasePlanPayload.recovery` (original publication job, current default-branch head and original tag creation time), `ReleaseJob.publicationJobId` / `reconciliationJobId`, and `ReleaseReceipt.evidence` (approval identity, observation time, interrupted step, exact object observations and recovery instruction). `ReleaseJob.attemptedEffects` and `ReleaseReceipt.evidence.attemptedEffects` optionally retain the ordered create-tag/create-release markers; older records without them remain valid and never authorize replay. The state store validates these fields when present; plans, intents and receipts remain immutable. Existing schema-1 records without these fields retain their previous interpretation. `ReleasePlanPayload.configurationDigest` is also optional for reading historical records, but new approval and execution require it; legacy plans must be prepared and approved again. This additive field is validated as a SHA-256 digest, not a secret or raw filesystem path. No token, key or raw subprocess output enters the new evidence.

Back up the entire private state directory with the owner stopped; cached checkouts alone are not a backup. Restoring interrupted jobs triggers read-only reconciliation. For rollback, stop the newer owner before starting older software. Older preparation/approval code still sees unresolved original publications and blocks them; a reconciled complete job without an older-style receipt also fails closed. Older software cannot continue the new recovery chain. Preserve the full state and return to a recovery-aware version rather than deleting records, importing partial state or bypassing the blocker. No destructive remote rollback is provided.
